# Startup-only workspace placement

Pinning an app edits its launcher/default workspace. It never relocates a running instance. A pin click first looks for an existing matching window on any workspace and focuses that window in place. The first open window uses the pinned workspace even if the app already has tray/background processes. Other open windows count across all workspaces, including inactive/cloaked workspaces.

The old unconditional native `move`/`focus` assignment rules are removed from the generated GlazeWM block. Its marker now enables `WorkspaceLaunchRouter`, owned by the CC application. The router subscribes to managed/unmanaged/config events and queries only after these events, with bounded settling reads only when a newly managed, configured app has not yet supplied its matching title/app identity, or its process identity is initially missing. It has no idle polling timer. Startup and reconnect snapshots establish a baseline without moving any existing window. Configuration edits and enabling rules cannot retroactively move baseline windows.

`WorkspaceLaunchPolicy` accepts a window only if its identity is new and no matching window already exists. Process names/PIDs are not used as proof of an open instance: Signal and similar tray apps can keep processes alive all day. Another matching managed window is what prevents assignment. Ambiguous app identities are left in place. An eight-second initial identity allowance is limited to the rules that existed when the window first appeared; adding or moving a pin during that interval cannot authorize a new destination.

Browser web apps share the browser executable. Their running state therefore means an existing window for that logical app, not every process named `chrome`. New web-app pins retain the window AppUserModelID and use it in backend matching. YouTube can start in workspace 7 while Helium remains in workspace 1. Subsequent YouTube windows are left where they open while another YouTube instance is present. Titles remain scoped for the taskbar display, and unidentified browser apps are rejected instead of creating process-wide pins.

Before moving, the router rechecks the target ID, rule fingerprint, enabled state and other matching windows. Its command targets the new window directly (`command --id ... move --workspace ...`); it never focuses a workspace or reloads configuration to perform placement. Disconnect/error recovery reseeds rather than replaying old windows. Application exit cancels the sockets and releases the router.

Checks cover first-window launches (including Signal reopened from its tray), existing/second windows, config/pin edits, reconnect, disabled/enabled rules, delayed identity beyond the first settling read, and shared-browser app identity. A read-only live check confirmed the installed GlazeWM accepts the lifecycle subscription and supplies the expected query fields. No live windows were moved in verification. Existing manually authored GlazeWM rules outside the owned block are unchanged and may still impose their own behavior.

On 2026-11-03, live inspection showed Signal processes dating from the morning. The former strict process-cohort check intentionally skipped that launch. The confirmed preference is now **no other open window**, not **no running process**. The router no longer enumerates processes on lifecycle events. It retries incomplete initial identity at 400 ms intervals for at most eight seconds; unrelated apps do not trigger these retries. Pin/config edits retain the same protection against retroactive moves.

On 2026-11-05, routing regression checks exposed two missed-launch cases: multiple matching first windows in one snapshot incorrectly blocked one another, and a removed/replaced window in the previous snapshot still counted as an open instance. New windows from the same initial snapshot now share a launch cohort; those peers are permitted during immediate move revalidation. Only matching windows still present outside that cohort block assignment. Windows with initially missing process names may settle against the rules captured at their appearance, and slow identity has up to eight seconds. Known unrelated processes still cause no settling reads. Successful targeted moves are logged in `wallpaper.log` with process, window ID and destination, without window titles. These cases are tested with synthetic Spotify windows; no live apps were moved during verification.
